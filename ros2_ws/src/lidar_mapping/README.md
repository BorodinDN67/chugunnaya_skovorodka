# lidar_mapping

Пакет для исходного Docker-стенда Unitree Go2 на ROS 2 Humble.
Compose монтирует существующий `ros2_ws` как `/ros2_ws`. Пакет находится в
`/ros2_ws/src/lidar_mapping`. Вычислительная библиотека `lidar_core` использует
C++17, Eigen и PCL. Узел локализации ROS 2 размещён в `src/ros_integration/`.

## Сборка и тесты

Из каталога стенда с оригинальным `docker-compose.yml` при работающем контейнере:

```powershell
docker exec -it r_hacatonius bash -l
```

В контейнере:

```bash
cd /ros2_ws
colcon build --packages-select lidar_mapping --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
colcon test --packages-select lidar_mapping --event-handlers console_direct+
colcon test-result --verbose
```

Манифест перечисляет зависимости сборки и тестов. Если в целевом образе
отсутствует тестовая зависимость `ament_cmake_gtest`, для запуска тестов
понадобится пакет `ros-humble-ament-cmake-gtest`. Сборка и тесты в Humble ожидают проверки.

## Вычислительные компоненты

- `CloudPreprocessor` принимает XYZ, удаляет неконечные координаты, применяет
  включительный радиальный диапазон относительно начала координат облака и
  передаёт остаток в PCL VoxelGrid. Нулевой размер вокселя отключает прореживание.
  Диагностика содержит четыре счётчика по стадиям обработки.
- `GICPRegistration` возвращает полную матрицу `source → target` с учётом начальной
  оценки. Fitness — средний квадрат расстояния в м² от каждой преобразованной
  точки source до ближайшей точки target. Доля соответствий имеет тот же
  знаменатель и учитывает только точки с расстоянием не больше
  `overlap_distance_m`. Этот порог задаётся независимо от
  `max_correspondence_distance_m`, используемого оптимизатором.
- Время GICP измеряется монотонными часами и включает входные проверки и
  диагностику. Матрица и метрики доступны при статусе `success`.
  `converged` отражает флаг PCL. В PCL 1.12 достижение лимита итераций может
  установить этот флаг. Пороги приёмки результата на реальных записях требуют
  отдельной настройки.
- `OdometryBuffer` принимает наносекундные метки и интерполирует позицию
  линейно, а ориентацию через SLERP. Предсказание строится по относительному
  движению между двумя одометрическими позами.

GICP локален и чувствителен к начальному приближению и геометрии. Препроцессор
работает с XYZ, без полей интенсивности, кольца и времени точки.

## ScanToMap

`ScanToMap(ScanToMapConfig, MapMode)` связывает буфер одометрии,
предобработку, предсказание SE(3), локальную карту и PCL GICP.
Будущий ROS 2 адаптер может использовать один из двух способов передачи одометрии.

- `push_odometry(stamp_ns, T_odom_robot)` и `process(scan, stamp_ns)` используют
  интерполяцию буфера. При отсутствии подходящего отсчёта результат позволяет
  повторить обработку после поступления одометрии.
- `process(scan, stamp_ns, T_odom_robot)` принимает уже синхронизированную позу.
  Переданный XYZ-скан должен находиться в системе робота. Кадры обрабатываются
  последовательно с возрастающими метками на одной временной шкале.

В mapping первое достаточно плотное облако ставится в начальную позу
(по умолчанию единичную). После инициализации ключевые кадры добавляются только
при принятой регистрации или в явно включённом режиме сравнения по одометрии.
Частота прореживания задаётся через `keyframes_per_downsample`.
`save_map("map_gicp.pcd")` сохраняет результат в директорию из `MapConfig`.
В localization требуются `load_map(filename)` и явный
`start_session(T_map_robot_initial)`. Режим задаётся при создании экземпляра.
Для новой записи можно вызовом `start_session` сбросить предыдущую одометрию,
временные метки и диагностику потери, сохранив загруженную карту.

Регистрация проверяет размер обоих облаков, сходимость, SE(3), fitness в м²,
долю соответствий и коррекцию относительно предсказания. Коррекция задаётся
в метрах и радианах. Матрица GICP уже переводит текущий скан в map.
При отклонении используется одометрическое предсказание с обновлением опорной
одометрии. После заданного числа подряд отклонённых кадров статус становится
`lost`. Принятая регистрация сбрасывает счётчик.

`ScanResult` содержит опциональные позы, совмещённое по итоговой позе облако,
статус кадра и отслеживания, метрики регистрации, флаги обновления карты и
время синхронизации, предобработки, предсказания, локальной выборки, GICP,
валидации, обновления карты и преобразования выходного облака. Отдельное поле
`total_ms` измеряет полный вызов. Нулевое время этапа может означать, что этап
пропущен. Совмещённое облако при отклонении отражает одометрическое предсказание.

### Синтетическое сравнение

`colcon test` запускает `lidar_synthetic`. Для отдельного прогона внутри
контейнера можно указать каталог артефактов:

```bash
cd /ros2_ws
./build/lidar_mapping/lidar_synthetic ./maps/synthetic
```

Сценарий генерирует трёхмерное помещение, панели, ограничение видимости по углам
и дальности, шум точек и дрейф одометрии. Для второй траектории используются
другое начало одометрии и явная исходная оценка позы.
Ожидаемые файлы после прогона:

- `odometry_only.pcd` и `odometry_gicp.pcd`.
- `odometry_only.csv`, `odometry_gicp.csv`, `localization.csv` с эталонными и
  оценёнными позами, ошибками, статусами и временами. Статусы в CSV — числовые
  значения `ScanStatus` и `TrackingStatus` из заголовка.
- `summary.csv` с RMSE положения и вращения, числом принятых регистраций
  и кадров со статусом потери.

Автоматический запуск сохраняет эти файлы в `build/lidar_mapping/synthetic`.
Ограничение видимости задаётся геометрически, без моделирования окклюзий лучей.
Синтетические пороги и метрики относятся только к этому сценарию.



## MapManager

`MapManager` хранит карту XYZ в памяти. В режиме mapping вызов
`add_cloud(scan, T_map_robot)` преобразует локальное облако в координаты карты,
добавляет его и запоминает позу принятого ключевого кадра. Первое корректное
облако инициализирует карту. Пустое облако, неконечные XYZ и некорректная
поза отклоняются. Перед передачей сырых данных можно использовать
`CloudPreprocessor`.

`should_add_keyframe(T_map_robot)` проверяет расстояние или угол относительно
последней принятой позы. Решение о вызове `add_cloud` остаётся у вызывающей стороны.
`downsample()` прореживает глобальную карту с помощью PCL VoxelGrid по явному вызову.
`local_map(center_in_map)` возвращает копию сферического участка в координатах
карты с помощью PCL KD-tree. `cloud()` предоставляет доступ к глобальной карте
для чтения.

`save_pcd(filename)` записывает двоичный PCD. `load_pcd(filename)` читает PCD с
конечными координатами XYZ типа FLOAT32. Оба метода принимают имя файла
внутри настроенной директории и возвращают `bool`. В режиме localization первая
успешная загрузка фиксирует карту до уничтожения экземпляра.
В режиме mapping успешная загрузка сбрасывает последнюю позу ключевого кадра.
PCD хранит геометрию карты, историю ключевых кадров следует вести отдельно.

Настройки `MapConfig` задаются при создании менеджера. Стартовые значения
ожидают проверки на записях.

| Поле | Значение |
| --- | --- |
| `voxel_size_m` | 0,05 м |
| `local_radius_m` | 10 м |
| `keyframe_translation_m` | 0,2 м |
| `keyframe_rotation_deg` | 10° |
| `directory` | относительный каталог `maps` |

Конфигурация для исходного Docker-стенда:

```cpp
lidar_core::MapConfig config;
config.directory = "/ros2_ws/maps";
lidar_core::MapManager map(config);
```

KD-tree строится при каждом запросе локальной карты. Синхронизацию при доступе
из нескольких потоков обеспечивает вызывающий код.
## Локализация на фиксированной карте

`lidar_localization` использует ядро `ScanToMap` в режиме localization.
Узел интерполирует `T_odom_base` на исходный штамп скана и передаёт позу в ядро.
В ядре прогноз `T_prev * inverse(O_prev) * O_now` служит начальной матрицей
PCL GICP. Источник — прореженный скан в `base_link`, цель — сферический участок
снимка PCD вокруг прогноза в `map`. При отклонении регистрации узел публикует
прогноз с диагностикой `fallback`. При отсутствии скобки одометрии скан
ждёт до 250 мс и получает `dropped`. Очередь ограничена восемью сканами.

| Топик | Сообщение |
|---|---|
| `/localization/pose` | `geometry_msgs/msg/PoseStamped` |
| `/localization/path` | `nav_msgs/msg/Path` |
| `/localization/map` | `sensor_msgs/msg/PointCloud2`, transient local |
| `/localization/aligned_cloud` | `sensor_msgs/msg/PointCloud2`, sensor-data QoS |
| `/localization/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` |

### Короткий прогон в Humble

Смонтируйте отдельный worktree как `/work` с правами только чтения. Поместите
распакованный bag в `/work/data/bag_for_localization`, проверенный снимок
карты первого этапа в `/work/results/localization/map_snapshot.pcd` и выделите
отдельное монтирование для результатов в `/out`. Используйте образ исходного
стенда с PCL либо дополните имеющийся образ Humble пакетами
`build-essential cmake python3-colcon-common-extensions libpcl-dev
ros-humble-pcl-conversions`.

```bash
export ROS_DOMAIN_ID=82 ROS_LOCALHOST_ONLY=1
source /opt/ros/humble/setup.bash
source /opt/unitree_msgs/setup.bash
pkg=/work/ros2_ws/src/lidar_mapping
CMAKE_BUILD_PARALLEL_LEVEL=2 colcon --log-base /out/log build \
  --base-paths "$pkg" --build-base /out/build --install-base /out/install \
  --packages-select lidar_mapping --executor sequential \
  --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
source /out/install/setup.bash

PLAY_SECONDS=10 PLAY_RATE=1.0 bash "$pkg/tools/run_localization.sh" \
  /work/data/bag_for_localization /work/results/localization/map_snapshot.pcd \
  /out/pilot '[1.56110,0.24249,0.33925,-0.03133,0.05347,0.81417]'
```

Вектор параметра `initial_pose_xyz_rpy` задаёт `T_map_base` на первом
синхронизированном скане в метрах и радианах. Числа в примере получены
сопоставлением начального фрагмента этой записи со снимком
`results/mapping-rechecked/map.pcd`. Для другой карты или точки старта
укажите свою начальную позу. Локальный GICP зависит от неё.

Скрипт сохраняет `bag-info.txt`, `input.json`, `input-scans.csv`,
`live-topics.txt`, `commands.log`, `environment.txt`, `trajectory.csv`,
`summary.json` и выходной MCAP. Он проверяет пустой
ROS-граф перед запуском, воспроизводит только два входа с `/clock` и загружает
конфигурацию `use_sim_time: true` из `config/localization.yaml`.
В RViz используйте Fixed Frame `map`. Для карты выберите Transient Local,
для совмещённого облака — Best Effort. Параметр `publish_map_to_odom`
по умолчанию выключен. Перед включением проверьте издателей
`ros2 topic info -v /tf` и `ros2 topic info -v /tf_static` и наличие
нужной ветки `odom -> base_link`. В выделенном графе без издателей TF
`RECORD_TF=1` включает обе дуги из оценок этого узла и записывает `/tf`.
`PLAY_SECONDS=full` оставляет проигрыватель до естественного конца.

Для визуальной проверки запустите `rviz2 -d` с
`config/localization-top.rviz` или `config/localization-follower.rviz` и
`--ros-args -p use_sim_time:=true`. Затем воспроизведите выходной MCAP
через `ros2 bag play`. В выходном bag уже есть `/clock`. Ракурс от
третьего лица использует `base_link`, поэтому для него требуется
выходной bag с `/tf`.

В CSV поле `pipeline_ms` включает синхронизацию, конвертацию, GICP и
публикации результата до диагностики. `processing_ms` измеряет ядро.
`queue_ms` измеряет ожидание с момента вызова ROS-подписки до обработки.
