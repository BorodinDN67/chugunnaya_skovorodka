## Облака и координаты

Во всех сканах `height=1`, `point_step=32`, little-endian и `is_dense=true`. Поля скалярные. `cloud` и `cloud_base` содержат `x`, `y`, `z`, `intensity`, `time` типа `FLOAT32` со смещениями 0, 4, 8, 16 и 24 байта и `ring` типа `UINT16` со смещением 20. В `cloud_deskewed` доступны только `x`, `y`, `z`, `intensity` с теми же типами и смещениями.

**Некорректные точки.** NaN/Inf в XYZ — **0%** во всех трёх топиках. В `cloud` и `cloud_base` нулевых троек нет. Каждый `cloud_deskewed` содержит ровно **10 000 начальных `(0,0,0)`**. Это 94,02% точек в mapping и 94,07% в localization. Размеры deskewed в таблице рассчитаны после исключения этих точек. Число оставшихся точек совпадает с `cloud_base` в каждой паре.

**Время точек.** `time` в `cloud` и `cloud_base` — смещение от `header.stamp` в секундах. Медианная длительность от первой до последней точки — 64,75 / 64,66 мс в mapping и 68,74 / 67,89 мс в localization соответственно. Точки встречаются с нестрогим порядком по `time`. Все `cloud_base` имеют точные пары с `cloud` по заголовку, в localization дополнительно записан один сырой скан. Метка каждой пары `cloud_deskewed` совпала с `cloud.header.stamp + max(cloud.time)` с абсолютной погрешностью ≤0,119 мкс. Внутри deskewed индивидуальные смещения отсутствуют. [Описание поля Unitree](https://github.com/unitreerobotics/unilidar_sdk/issues/6)

**Проверка координат.** В 34 / 31 выборочном скане `cloud_base` — подмножество сырого облака после жёсткого преобразования из `utlidar_lidar` в `base_link`. Парные точки сопоставлены по `(time, ring)`, медианный остаток подгонки около `3×10⁻⁸ м`. После применения к `cloud_base` интерполированной позы `T_odom_base` медианный попарный остаток до очищенного `cloud_deskewed` составил 1,47 / 1,73 см. Для контрольной карты точки `cloud_deskewed` уже находятся в `odom` своей записи и готовы к накоплению после очистки.

## Одометрия, синхронизация и TF

`robot_odom` содержит положение `pose.pose.position.{x,y,z}` в метрах и кватернион `pose.pose.orientation.{x,y,z,w}` в `odom`. `child_frame_id=base_link`. В `twist.twist` записаны линейная и угловая скорости в дочернем кадре. Неконечных поз нет. `robot_pose` содержит позицию и кватернион без дочернего кадра и без скоростей. Все 2263 / 2056 его сообщений совпали с `robot_odom` по метке и значениям позы. Это прореженная оценка той же одометрии.

| Параметр `robot_odom` | Mapping | Localization |
|---|---:|---:|
| Диапазон X / Y / Z, м | −2,497…3,492 / 0,050…15,500 / 0,272…0,319 | −2,236…3,831 / 0,478…15,115 / 0,267…0,326 |
| Длина траектории / смещение от старта к финишу, м | 42,207 / 2,216 | 44,936 / 2,126 |
| Норма линейной скорости min / p50 / p95 / max, м/с | ≈0 / 0,368 / 0,711 / 1,202 | ≈0 / 0,243 / 1,101 / 2,576 |
| Норма угловой скорости min / p50 / p95 / max, рад/с | 0,001 / 0,197 / 1,146 / 2,803 | 0,001 / 0,435 / 2,024 / 3,040 |

В каждом из пяти основных топиков `header.stamp` строго возрастает. Нулевых меток, повторов и откатов внутри топиков нет. Медиана `record_time − header.stamp` составляет 80,893 / 80,898 с для `cloud_base` и 80,824 / 80,826 с для `robot_odom`. Это разница двух шкал времени в файле. Для интерполяции нужно использовать метки заголовков обоих потоков, а время записи оставить для планирования воспроизведения.

Точных пар `cloud_base` ↔ `robot_odom` по метке нет. Во всех парах с двумя опорами поздняя опора уже присутствовала к моменту записи скана. Для `cloud` покрытие одометрией 1686/1688 и 1525/1526, для `cloud_deskewed` — 1687/1688 и 1525/1525. Сканы до первой опоры требуют явного пропуска или отдельной диагностики.

**TF.** В обоих MCAP нет `/tf`, `/tf_static`, `/clock` и сообщений `tf2_msgs/msg/TFMessage`. Временное преобразование `odom → base_link` доступно из `robot_odom`. Калиброванные статические TF `base_link ↔ utlidar_lidar` и `base_link ↔ utlidar_imu`, а также `map → odom` в записях отсутствуют. Для входа `cloud_base` дополнительное преобразование лидара не требуется.
